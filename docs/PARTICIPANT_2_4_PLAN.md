## Действия после выдачи контроля

**Первые 5 минут.** № 4 получает точный `group_id` и сверяет источник. Если организаторы выдали новую ссылку на API, обновить локальную настройку по [инструкции импорта](ZIP_INTEGRATION.md). На компьютере команды нужен запущенный модельный API с Google-ключом и настроенным маршрутом Gemma 4. [Запуск API](PARTICIPANT_2_HANDOFF.md)

**Следующие 30 минут и до 10 минут на повторы.** Из корня репозитория выполнить:

```powershell
$group = Read-Host 'Точный group_id от организаторов'
.\.venv\Scripts\python.exe -m scripts.run_control --group-id $group
```

Команда проверяет подключённую модель, импортирует группу, сверяет наличие десяти чатов и использует исходный чек-лист `freedom-chat@1`. Одновременно оцениваются до двух диалогов. После первого прохода пишется проверенный файл. Для технически неуспешного задания предусмотрен один повтор на Gemma 4, затем файл обновляется. Команда сообщает ID оставшихся ошибок. Если терминал закрылся, повторить команду с тем же ID группы. При нехватке времени или повторной технической ошибке смотреть исходные задания командой `backend.app.submission status prod --group-id $group`. [Ручной экспорт](../results/README.md)

**Последние 10–15 минут.** № 4 проверяет выгрузку и число ошибок:

```powershell
.\.venv\Scripts\python.exe -m backend.app.submission check prod --group-id $group
git status -sb
git add -- results/prod/results.json
git diff --cached --stat
git commit -m "Submit WE ARE GROOT control results"
git push
```

Если работа идёт в командной ветке, завершить слияние в `main`. Открыть DEV и PROD непосредственно в GitHub и убедиться, что в контрольном файле десять выданных ID. При ошибке после реальной попытки формат допускает строку `error` с причиной. Оригиналы диалогов, записи и ключи остаются в локальном хранилище.
