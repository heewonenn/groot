# Общий контракт данных CQA

Действующий контракт — `team-v1` от 7 ноября 2026 года, согласованный с `CQA-team.zip` по прямому указанию пользователя. Общий чат — p1-ru-001, сервер — 8765. API данных ZIP, чек-листов и общий расчёт подключены к одному FastAPI. Оценка моделью и апелляции остаются задачами интеграции. [Описание перехода](../ZIP_INTEGRATION.md), [API участника 1](../PARTICIPANT_1_HANDOFF.md).

## Идентификаторы

API возвращает `group_id`, `conversation_id`, `channel`, `language`, `message_count` и `transcript`. В карточке также есть `has_audio` и `audio_url`; локальные выдержки ZIP могут их опускать. Каждая реплика содержит исходные timestamp, speaker, text и добавленный `message_id`.

Номер сообщения начинается с единицы в исходном массиве до фильтрации: `message_id = conversation_id + ":m" + номер`, дополненный нулями минимум до четырёх цифр. Например, первая реплика оператора в общем чате — `p1-ru-001:m0010`. Одинаковые timestamp не объединяют реплики.

Полная ссылка всегда включает **group_id + conversation_id + message_id**. Один message_id без группы не гарантирует уникальность. Модель возвращает эти поля, карточка использует `GET /api/groups/{group_id}/conversations/{conversation_id}/messages/{message_id}`. Значения компонентов пути необходимо URL-кодировать.

Повтор идентичного импорта сохраняет ID. Изменение текста, роли, порядка, времени, канала или языка уже импортированного диалога либо его исчезновение из той же группы возвращает 409 и откатывает всю загрузку. Обновление audio_url допустимо. UUID версии диалога в новом формате не требуется: прежний текст защищён запретом перезаписи. Разные группы независимы. Версия чек-листа по-прежнему обязательна в оценке.

## Время и аудио

`timestamp` содержит исходную строку: MM:SS у чатов, ISO 8601 у звонков. Вычитание первой метки времени не гарантирует позицию в записи. API ZIP не отдаёт проверенные смещения по каждой реплике. `audio_url` может вести на HTML-плеер; его нельзя без проверки считать прямым MP3 для элемента audio.

До отдельной синхронизации показывается открытие записи, а точный переход ко времени не обещается. README архива сообщает о двух сопоставленных фрагментах одного звонка; при этой интеграции запись повторно не прослушивалась. Проверка всех пяти звонков и плеер остаются задачами участника 4. Модель не придумывает смещения.

## Версии чек-листов

`checklist_id` обозначает семейство правил, `checklist_version_id` — неизменяемый снимок. При первом запуске хранилище создаёт `freedom-chat@1` и `freedom-call@1`. Учебная `freedom-chat@2` остаётся примером: приложение создаёт следующую версию из фактически сохранённых изменений пользователя. Номера генерируются сервером в транзакции, отдельные копии получают новые семейства ID.

`previous_version_id` связывает версии одного чек-листа. `derived_from_version_id` связывает копию звонков с исходным чатовым чек-листом. После копирования правила независимы. Для любой оценки необходимо получить весь снимок по `GET /api/checklist-versions/{version_id}`.

Каждая ступень имеет `value`, `description` и `normalized_value`. Вес берётся из конфигурации. `normalized_value` хранится десятичной строкой; для базовых шкал это значение, делённое на максимум. Для флага вес равен нулю, `flag_when = true`, положительный ответ означает найденную грубую ошибку.

## Ответ модели и ответ карточки

Модель возвращает model_result с group_id, conversation_id, checklist_id и checklist_version_id: по каждому критерию есть value, applicability, обоснование и доказательства. Для N/A value=null, applicability=not_applicable и заполнен na_reason. Для недостатка данных используется decision_status=unresolved; это не N/A. Полный ответ модели и история пересмотра — расширение одно-критериального примера ZIP; составная ссылка на реплику сохраняется без изменения.

Сервер формирует `evaluation_response`. Он хранит неизменённый `model_result`, рассчитанный `original_result`, историю `review_history` и рассчитанный `final_result`. Без апелляций final_result совпадает с original_result. При пересмотре оригинал не перезаписывается. Критерий, новое значение и причина решения берутся из истории; окончательный расчёт выполняется по исходной версии чек-листа.

| Поле расчёта | Смысл |
| --- | --- |
| `raw_value` | Принятый ответ критерия; в финальном расчёте может отличаться от исходного модельного |
| `weight` | Исходный вес из снимка правил |
| `normalized_value` | Доля от 0 до 1; для N/A и флага — null |
| `earned_points` | Баллы до перераспределения веса, `weight × normalized_value` |
| `effective_weight` | Вес после исключения N/A и нормирования на 100 |
| `weighted_contribution` | Вклад критерия в итог после перераспределения |
| `applicable_weight` | Сумма исходных весов применимых оцениваемых критериев |
| `total` | Итог до двух знаков; null при отсутствии применимого веса |
| `gross_error` | Отдельный флаг, не влияющий на total |

Денежные по форме десятичные строки здесь обозначают баллы, а не валюту. Веса и ступени передаются JSON-числами; баллы и нормированные доли — десятичными строками. Итог и исходные баллы показываются до двух знаков, эффективные веса и вклады в примере — до четырёх. Производственный расчёт хранит промежуточные значения без округления; клиент не пересчитывает итог из отображаемых строк.

`original_result.sections` и `final_result.sections` содержат вклад каждой секции в общий итог и отдельный `local_percent` внутри секции. Локальные проценты не складываются. Секция без применимого веса имеет `local_percent = null`; секция грубых флагов не приносит баллов.

В исходном чек-листе для N/A и флага `earned_points`, `effective_weight`, `weighted_contribution` равны null: эти строки не входят в балльный расчёт. У применимого ответа «Нет» вклад равен нулю, но вес остаётся в знаменателе.

При `partial` или `failed` невозможно показывать полный итог из только удачных критериев. До поддержки подробного частичного расчёта можно вернуть `original_result = null`, `final_result = null`, сохранив доступные ответы и причины в model_result. Для полного транспортного сбоя model_result также допускает null; подробная ошибка находится в состоянии задания согласно ТЗ.

## Доказательства

Каждый элемент evidence содержит `group_id`, `conversation_id`, `message_id` — как в примере ZIP. Расширение для полной оценки добавляет `kind` (support, absence, context) и при необходимости `span.start_message_id` / `span.end_message_id`. Границы включительные и относятся к тому же диалогу; порядок берётся из transcript. Для нескольких реплик передаётся несколько элементов evidence. Для пропущенного действия используется absence с участком ожидаемого действия. В review_history также используется список составных ссылок evidence.

В model_result текст цитаты не требуется: сервер и карточка извлекают его из сохранённого транскрипта по полной составной ссылке. Ссылки на несуществующий ID или другой диалог/группу не принимаются. Для проверки идентификации модель может использовать связанное системное событие, но не приписывать оператору приветствие бота.

## Проверки за пределами JSON Schema

JSON Schema проверяет структуру и типы. Сервер отдельно обязан проверить полный и уникальный набор критериев, совпадение внешних ID и версий на всех уровнях, принадлежность доказательств диалогу, порядок границ диапазона, соответствие value типу и ступеням критерия, разрешение N/A, ненулевые веса балльных критериев, уникальность секций и ступеней, корректность нормированных значений и арифметику.

Число `true` не должно проходить как числовая ступень 1 при валидации Python. Одинаковый ID версии с другим содержимым запрещён. Для апелляции учитывается версия первоначальной оценки, а не текущий черновик редактора.

## Как применять примеры

Участник 3 может начать с пары synthetic conversation/server response, затем переключиться на локальные chat/server response из DEV без изменения структуры экрана. Демонстрационная пометка должна оставаться видимой. Все примеры ответов имеют `use_for_model_quality = false` и не включаются во внутренний benchmark.

Наборы scoring-cases являются проверками функции участника 1, а не сетевым API. Поле `test_only_criterion_subset` создаёт отдельную искусственную конфигурацию теста из перечисленных критериев; оно не разрешает менять состав сохранённой версии в рабочем приложении.
