# Участник 1: чек-листы, версии и расчёт

Дата: 7 ноября 2026 года. Инструкция по готовому модулю для команды CQA.

Действующая интеграция следует CQA-team.zip: общий сервер 8765, чат p1-ru-001, ссылки group_id + conversation_id + message_id. API данных и чек-листов объединены. [Подключение по ZIP](ZIP_INTEGRATION.md).

Для объяснения роли простыми словами, ручной приёмки и использования Codex смотрите [инструкцию участника 1](PARTICIPANT_1_GUIDE.md).

## Что реализовано

- React-редактор по адресу `/checklists`: создание, копирование сохранённой версии, изменение и удаление критериев, порядок, секции и каналы.
- Настройка формулировок, весов, типов ответа, числовых ступеней и их описаний, условий N/A и отдельного флага нарушения.
- Два исходных чек-листа из согласованных конфигураций: `freedom-chat@1` и `freedom-call@1`. Для звонков уже включена адаптация критериев 04 и 06.
- Черновики и неизменяемые сохранённые версии в SQLite. Изменение черновика не изменяет ранее сохранённый снимок.
- Один расчёт на Python для автоматической оценки и пересмотра. Проверка полного набора критериев, допустимых ответов, N/A и округление Decimal `ROUND_HALF_UP`.
- Ручная проверка арифметики через интерфейс и настоящий API, включая примеры 85,38 и 93,08.
- Защита от перезаписи чужого черновика через номер `revision`; понятные ошибки, повтор загрузки и адаптация интерфейса к узкому экрану.

Редактор не вызывает AI. Кнопка «После пересмотра 93,08» подставляет учебные ответы для проверки функции расчёта; история настоящей апелляции — задача участника 3. Итоги расчёта этот модуль не сохраняет как оценки диалогов: их хранение выполняют модули участников 3 и 4.

## Запуск и быстрая демонстрация

В первом PowerShell из корня репозитория:

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --reload --host 127.0.0.1 --port 8765
```

Во втором терминале:

```powershell
cd frontend
npm run dev
```

Открыть [редактор](http://127.0.0.1:5173/checklists). Описание запросов доступно в [FastAPI OpenAPI](http://127.0.0.1:8765/docs).

1. Выбрать чатовый чек-лист, нажать «Копия» и дать ей название. Сохранить первую версию.
2. Изменить правило или описание ступени, сохранить следующую версию. Выбрать старую версию в списке: её поля доступны только для просмотра и сохраняют прежний текст.
3. Перезагрузить страницу: выбранное семейство чек-листа и его сохранённый черновик восстанавливаются.
4. Открыть исходный `freedom-chat`, перейти в «Проверка расчёта», нажать «Пример 85,38», затем «После пересмотра 93,08».
5. Вернуться к первому примеру, изменить критерий 02 с N/A на «Да» и рассчитать: получится 88,13. Включение флага 08 не меняет итог.

Для повторения демонстрации безопаснее создавать копию, чтобы исходные правила оставались удобной точкой сравнения. Изменения становятся доступны модели только после сохранения версии.

## API чек-листов

Все пути ниже начинаются с `/api`. Полные схемы запросов и ответов находятся в OpenAPI работающего сервера. Снимок `ChecklistVersion` соответствует `docs/contracts/cqa-team-v1.schema.json`; структуры черновика и входа расчёта определены в `backend/app/schemas/checklists.py`.

| Метод и путь | Назначение | Тело |
| --- | --- | --- |
| `GET /checklists` | Список семейств, последняя версия, состояние черновика | — |
| `POST /checklists` | Создать пустой черновик или независимую копию версии | `{"title":"Мои правила","copy_from_version_id":"freedom-chat@1"}`; для пустого опустить `copy_from_version_id` |
| `GET /checklists/{id}/draft` | Получить черновик, `revision` и `base_version_id` | — |
| `PATCH /checklists/{id}/draft` | Сохранить полную конфигурацию черновика | `{"expected_revision":1,"content":{...}}` |
| `GET /checklists/{id}/versions` | Все сохранённые версии, новые сначала | — |
| `POST /checklists/{id}/versions` | Создать неизменяемый снимок текущего черновика | `{"expected_revision":2}` |
| `GET /checklist-versions/{version_id}` | Получить ровно указанную версию | — |
| `POST /checklist-versions/{version_id}/calculate` | Рассчитать принятые ответы | `{"answers":[...]}` |

Числа `expected_revision` в таблице — пример, их всегда нужно брать из последнего ответа сервера. После публикации следует заново получить черновик. Если версия уже содержит тот же контент, повторная публикация возвращает её без создания дубликата. Черновик может быть без критериев; публиковать пустой чек-лист нельзя.

Ошибки возвращаются как `{"error":{"code":"...","message":"...","details":[],"request_id":"..."}}`. Основные статусы: 404 — неизвестный ID; 409 — устаревший `revision`; 422 — неверные правила или ответы; 503 — недоступное хранилище. При 409 нужно получить свежий черновик и согласовать изменения, а не повторять старый запрос вслепую.

### Пример входа расчёта

`POST /api/checklist-versions/freedom-chat@1/calculate`:

```json
{
  "answers": [
    {"criterion_id":"01","value":true,"applicability":"applicable"},
    {"criterion_id":"02","value":null,"applicability":"not_applicable"},
    {"criterion_id":"03","value":null,"applicability":"not_applicable"},
    {"criterion_id":"04","value":15,"applicability":"applicable"},
    {"criterion_id":"05","value":true,"applicability":"applicable"},
    {"criterion_id":"06","value":7,"applicability":"applicable"},
    {"criterion_id":"07","value":true,"applicability":"applicable"},
    {"criterion_id":"08","value":false,"applicability":"applicable"}
  ]
}
```

Ответ содержит `checklist_version_id` и `result`. В этом примере `result.total = "85.38"`, `applicable_weight = "65.00"`, `earned_points = "55.50"`. В `criteria` находятся исходные значения, веса, нормированные доли, баллы до перераспределения и вклады после него; в `sections` — результаты секций. Грубая ошибка передаётся отдельно в `gross_error`.

Поле `decision_status` входного ответа по умолчанию равно `evaluated`. Если модель не смогла принять решение, передавайте `unresolved`: расчёт вернёт ошибку, и весь модуль оценки должен сохранить незавершённый статус. Нельзя превращать недостаток информации в N/A или молча считать недостающий критерий нулём.

### Вызов из Python

```python
from backend.app.schemas.checklists import ScoringAnswer
from backend.app.services.scoring import calculate

# repository — полученный через dependency injection ChecklistRepository.
version = repository.get_version(evaluation_checklist_version_id)
answers = [ScoringAnswer.model_validate(item) for item in accepted_answer_dicts]
result = calculate(version, answers)
result_payload = result.model_dump(mode="json")
```

`accepted_answer_dicts` содержит только `criterion_id`, `value`, `applicability`, `decision_status`. Не передавайте весь `model_result` в `ScoringAnswer`: обоснования, цитаты и ссылки проверяются и хранятся модулем оценки отдельно. Сам калькулятор не читает диалог и не проверяет истинность обоснования N/A. Он проверяет, разрешён ли N/A конфигурацией, и правильность представления ответа.

Калькулятор не обращается к базе, сети или AI. На вход подаются уже загруженный снимок правил и все принятые ответы. При апелляции используется версия из сохранённой оценки, даже если редактор уже создал более новую версию.

## Хранение и границы модулей

По умолчанию база — `data/cqa.sqlite3`, исключённая из Git. Другая база задаётся через переменную процесса `CQA_DB_PATH`. `.env` автоматически не загружается. Путь не следует передавать во frontend.

Репозиторий участника 1 владеет только таблицами `cqa_checklists` и `cqa_checklist_versions`; создаёт их и исходные правила идемпотентно. Повторное открытие базы не перезаписывает пользовательские изменения. Сохранённые версии через API нельзя обновить или удалить. При будущей общей миграции участник 4 должен сохранить эти таблицы и их ID.

| Код | Владелец |
| --- | --- |
| `backend/app/schemas/checklists.py`, `api/checklists.py`, `repositories/checklists.py`, `services/scoring.py` | Участник 1 |
| `backend/app/resources/checklists/` | Участник 1; стартовые копии согласованных конфигураций |
| `frontend/src/features/checklists/` | Участник 1 |
| `backend/tests/test_scoring.py`, `test_checklists_api.py`, `frontend/tests/checklists.spec.ts` | Участник 1 |
| Подключение router в `backend/app/main.py`, страницы в `frontend/src/App.tsx`, изоляция БД в `frontend/playwright.config.ts` | Сделано для запуска модуля; дальнейшее объединение координирует участник 4 |

Существующая стартовая страница и `/api/health` сохранены. Новых зависимостей модуль не добавляет: SQLite входит в Python. В production нужен маршрут frontend и проксирование `/api`; dev-прокси Vite не заменяет конфигурацию развёртывания.

Редактор при изменении числовых значений ступеней назначает доли линейно от минимума к максимуму и показывает процент веса. Изменение только описания сохраняет прежнюю долю. Калькулятор использует сохранённые `normalized_value`, включая нелинейные шкалы, переданные через API; не выводит их из значения самостоятельно.

## Проверка и оставшиеся границы

Запуск полной проверки из корня: `pwsh -File scripts/verify.ps1`. Перед ней нужно остановить dev-серверы: тесты используют порты 8765 и 5173. Браузерные тесты создают временную базу с искусственным диалогом; пользовательская база не затрагивается.

До подключения ZIP проверка модуля участника 1 завершилась с кодом 0: 25 Python-тестов и 6 браузерных тестов, включая стартовые проверки. Из них модулю участника 1 относятся 22 Python-теста и 4 браузерных сценария. Скриншоты настольного редактора, расчёта и мобильного вида просмотрены. Актуальная проверка общей сборки описана в [интеграции ZIP](ZIP_INTEGRATION.md). Проверены следующие сценарии:

- Девять общих векторов арифметики, полный набор ответов, неверные типы, запрещённый N/A, неизвестная ступень и незавершённое решение.
- Схема исходных версий, API создания и копирования, конфликт редакций, неизменяемость старой версии, её расчёт после изменения шкалы и повторное открытие SQLite.
- Настоящие frontend/API: создание и редактирование, изменение смысла и значения ступени, история, восстановление после обновления страницы, ручной расчёт, клавиатура, узкий экран и восстановление после сетевой ошибки.
- Отсутствие путей и внутренних сообщений SQLite в ответе при недоступном хранилище.

В текущих зависимостях есть предупреждение Starlette о будущем переходе TestClient с `httpx` на `httpx2`; оно не мешает прохождению тестов. Для запуска проверки понадобился доступ к локальным сокетам вне песочницы: при ограничении loopback даже стартовый TestClient зависал. Это ограничение среды проверки, а не требование к внешней сети или платному сервису.

Примеры 85,38 и 93,08 — тесты арифметики, не Ground Truth и не метрики AI. Проверка влияния новой формулировки на настоящий вывод модели требует подключения участника 2. Импорт DEV и получение реплики по message_id подключены из ZIP. Реальные апелляции, доказательства модели и плеер остаются за соответствующими участниками. Установка на новом компьютере из lockfiles и полное развёртывание продукта не проверялись.
