# План первой сборки CQA для четырёх участников

Версия 1.1 от 7 ноября 2026 года. Дополнение к [ТЗ](TECHNICAL_SPECIFICATION.md). По указанию пользователя используем привязки, общий чат и сервер из CQA-team.zip: message_id, p1-ru-001, порт 8765. Модуль участника 1 и API данных из ZIP объединены; реальный inference, апелляции и аудиоплеер ещё предстоит реализовать. [Интеграция ZIP](ZIP_INTEGRATION.md).

## 1 Общие примеры

| Назначение | Диалог | Почему выбран | Локальный файл |
| --- | --- | --- | --- |
| Первый общий чат | `p1-ru-001`, 12 реплик | Общий чат из ZIP; первая реплика оператора имеет message_id p1-ru-001:m0010 | [chat.json](../data/examples/team-zip-v1/chat.json) |
| Первый общий звонок | `p4-ru-001`, 45 реплик | Самый короткий звонок DEV; есть системные события, повторяющиеся время и текст, приостановка и возобновление записи | [call.json](../data/examples/team-zip-v1/call.json) |
| Проверка изменения критерия | `p1-ru-014`, 14 реплик | В первой реплике оператор здоровается, но не представляется | [checklist-change-chat.json](../data/examples/team-zip-v1/checklist-change-chat.json) |

Эти файлы содержат реальные записи DEV и находятся в исключённой из Git папке `data`. Подписанные ссылки удалены из нормализованных представлений. Оригинальный ответ API сохраняется отдельно в `data/raw`. Обмен реальными записями между участниками выполняется через разрешённый доступ к DEV, а не через публичный репозиторий.

Для работы без DEV в репозитории есть [искусственный диалог](contracts/examples/conversation.synthetic.json) и [ответ сервера к нему](contracts/examples/server-response.synthetic.json). Они предназначены для разработки интерфейса и проверки расчёта.

## 2 Четыре общих соглашения

### Постоянный ID реплики

Участник 4 выдаёт message_id вида p1-ru-001:m0010, нумерация с единицы в исходном transcript. Модель и карточка сохраняют тройку group_id, conversation_id, message_id без преобразования. Повтор неизменённого импорта сохраняет ID; изменение уже сохранённого диалога в той же группе отклоняется с 409, как в ZIP. [Действующий контракт](contracts/README.md).

Время не является ключом. Одинаковые реплики сохраняются отдельно; удалять их как дубликаты при импорте нельзя. Номер message_id не пересчитывается после скрытия бота или системных событий.

### Версия правил в каждой оценке

Оценка содержит group_id, conversation_id, checklist_id и checklist_version_id. Участник 1 предоставляет полную конфигурацию по GET /api/checklist-versions/{version_id}. Участник 2 получает неизменяемую версию правил, участник 3 показывает её в карточке и сохраняет при апелляции. conversation_version_id из старого контракта больше не требуется.

Готовы начальные [правила чатов](contracts/checklists/chat-v1.json) и отдельная [копия для звонков](contracts/checklists/call-v1.json). `freedom-call@1` ссылается на исходную `freedom-chat@1`, но принадлежит отдельному чек-листу. Описания ступеней и условия N/A передаются модели вместе с весами и типами ответов.

### Ответ модели и арифметика отдельно

`model_result.criteria[].value` хранит исходный ответ модели. `original_result.criteria[]` хранит проверенные и рассчитанные значения: `raw_value`, `weight`, `earned_points`, `effective_weight`, `weighted_contribution`. Например: `value = 7`, `weight = 15`, `earned_points = "10.50"`.

Числа `earned_points` даны до перераспределения N/A. `weighted_contribution` — вклад в итог после перераспределения. При применимом весе 65 для критерия 06 с оценкой 7 они равны 10,50 и примерно 16,1538 соответственно. Интерфейс не должен называть эти разные величины одним неуточнённым полем «баллы».

### Один пример ответа сервера

Для выбранного чата подготовлены [исходный модельный DTO](../data/examples/team-zip-v1/model-result.example.json) и [полный ответ карточки](../data/examples/team-zip-v1/server-response.example.json). В полном ответе есть исходный результат, учебная апелляция, решение и финальный результат. JSON проходит общую [JSON Schema](contracts/cqa-team-v1.schema.json).

Все эти ответы помечены `generation.mode = demo`, `origin = hand_authored_contract_fixture`, `is_ground_truth = false`, `use_for_model_quality = false`. Оценки назначены для проверки контракта и арифметики. Это не настоящий вызов модели, не экспертная разметка выбранного чата и не материал для измерения точности. К шестому часу участник 2 должен заменить демонстрационный ответ реальным inference с теми же связями ID.

## 3 Закреплённая арифметика

| Критерий | Исходный ответ | После учебного пересмотра |
| --- | --- | --- |
| 01 | Да | Да |
| 02 | N/A | N/A |
| 03 | N/A | N/A |
| 04 | 15 | 20 |
| 05 | Да | Да |
| 06 | 7 | 7 |
| 07 | Да | Да |
| 08 | Нет | Нет |

Применимый вес в обоих случаях — 65. До пересмотра: `10 + 15 + 15 + 10,5 + 5 = 55,5`; итог `55,5 / 65 × 100 = 85,38`. После пересмотра 04: `60,5 / 65 × 100 = 93,08`.

При независимом изменении исходного 02 с N/A на «Да» числитель становится 70,5, знаменатель — 80, итог — 88,13 при `ROUND_HALF_UP`. Этот пример проверяет не только числитель, но и знаменатель. Он также выявляет ошибку использования банковского округления на значении 88,125.

Готовы [девять наборов входов и ожидаемых результатов](contracts/examples/scoring-cases.json): перевод 7/10 в 10,50; 85,38; 93,08; N/A → Да; отсутствие применимого веса; независимость грубого флага; недопустимая ступень 8; запрещённый N/A для 06; boolean вместо числовой ступени. Участник 1 переносит их в тесты производственного расчёта. Подмножества критериев в двух кейсах являются отдельными искусственными тестовыми конфигурациями, а не изменением сохранённой `freedom-chat@1`.

Пример 77,69 из исходного ТЗ также остаётся корректным: в нём исходная оценка 04 равна 10, а не 15.

| 3 — карточка и апелляции | `frontend/src/features/dialogues/`, `frontend/src/features/evaluations/`, `frontend/src/features/appeals/`, `backend/app/api/appeals.py`, `services/appeals.py`, `repositories/appeals.py`, `schemas/appeals.py`, тесты апелляций | Карточка, переход к репликам, решение проверяющего, история и вызов общего расчёта |

Участник 4 интегрирует общую схему `docs/contracts/cqa-team-v1.schema.json` после согласования с участниками 1–3. Он же владеет общим инициализатором SQLite и подключением роутеров; участники передают ему необходимые таблицы и точки подключения. Никто не создаёт второй независимый расчёт или отдельный формат ID.

Согласуемая сигнатура участника 1: `calculate(checklist_version, criterion_answers) -> CalculatedResult`. Участник 2 не вычисляет баллы в prompt. Участник 3 собирает финальные ответы из исходной оценки и решений по апелляциям и передаёт их этой же функции. Участник 4 сохраняет исходный и финальный расчёт с исходной версией чек-листа.

## 5 Задания и результаты участников

### Участник 1

Перенести подготовленные конфигурации в хранилище, реализовать получение по ID версии и редактор. Пользователь редактирует не только значение ступени, но и её смысл. Изменение использованной версии создаёт новую. Реализовать общий расчёт с проверкой полного набора критериев, разрешённых значений, N/A и Decimal-округления. Подключить девять наборов проверок и отдельную проверку отсутствующего критерия.

К шестому часу: сохранённый чек-лист, работающий запрос его полной конфигурации и расчёт одного диалога. Для звонков используется отдельная копия; изменения её критерия 06 не переписывают чатовый чек-лист.

### Участник 2

Передавать модели язык, канал, group_id, conversation_id, transcript с message_id и ролями, всю конфигурацию выбранной версии чек-листа, включая пояснения к ступеням. Проверять полноту и уникальность критериев, тип ответа, принадлежность доказательств нужной группе и диалогу и обоснование N/A. Повторять некорректный ответ только в пределах установленного бюджета; при неуспехе возвращать явный статус, а не подставлять демо-оценку.

Проверить хотя бы по одному RU-, KZ- и EN-чату вручную. На `p1-ru-014` выполнить сценарий изменения критерия 01. Для ошибочного тарифа требовать продуктовый источник. Для выводов о темпе и дикции фиксировать реальное использование аудио. Измерять время и стоимость всех вызовов, включая повторы.

К шестому часу: один настоящий модельный результат по `p1-ru-001` с доказательствами. Он не обязан совпадать с демонстрационными 85,38 — это число не является эталоном DEV.

### Участник 3

Начать карточку на готовом ответе сервера с видимым режимом demo. Показывать выбранную ступень, исходный вес, баллы до перераспределения и итоговый вклад. Разместить транскрипт рядом с критериями; переход выполнять по ID, включая фрагменты за пределами первого экрана. Подключить аудиокомпонент участника 4.

Реализовать комментарий апелляции, подтверждение или изменение допустимого ответа с причиной. Сохранять решение и вызывать общий расчёт. Проверить восстановление карточки после обновления страницы. Апелляция после появления `freedom-chat@2` всё равно рассматривается по исходной версии оценки `freedom-chat@1`.

К двенадцатому часу: на реальном чате работают доказательство, апелляция, решение, пересчёт и восстановление исходного и финального результата после перезагрузки.

### Участник 4

Импорт ZIP уже подключён в backend/app/team_data.py: group_id, проверка isSuccess и data.records, отсутствие дублей, постоянные message_id и откат при конфликте. Участник 4 продолжает пакетные статусы, сохранение результатов по мере готовности и повтор неуспешных записей. Карточка получает audio_url согласно ZIP; точный переход к фрагменту требует отдельно проверенных смещений.

Проверить все пять звонков по ранней и поздней фразе, включая события паузы и возобновления. README ZIP сообщает о двух сопоставленных фрагментах p4-ru-001; эта информация не подтверждает синхронизацию всех реплик. Если аудио исключает паузу, нужен учёт сегментов; абсолютное время относительно первой реплики не является готовой позицией плеера.

Замерить полный прогон DEV после подключения реальной модели. Подготовить README, установку из lockfiles и запуск на чистой копии. Контроль загружается новым `group_id`. Публикация репозитория и отправка ссылки организаторам выполняются владельцем либо после его явного разрешения, с исключением секретов и записей из Git.

## 6 Сценарий изменения критерия

1. Импортировать p1-ru-014; использовать ссылку DEV / p1-ru-014 / p1-ru-014:m0010.
2. По `freedom-chat@1` критерий 01 требует приветствие и представление. Ожидаемый ответ — «Нет»: оператор не представился.
3. Через редактор убрать требование представиться, сохранив язык и первое приветствие. Сохранить новую версию.
4. Оценить тот же диалог с новой версией. Ожидаемый ответ по 01 — «Да» с той же репликой-доказательством.
5. Открыть обе оценки. Старые правила и исходный ответ не изменились; новая оценка не пришла из кеша старой версии.

Подготовлены [конфигурация версии 2 для сверки](contracts/checklists/chat-v2-greeting-only.example.json) и [описание ожидаемого сценария](../data/examples/team-zip-v1/checklist-change.expectations.json). Это критерий приёмки на наблюдаемом тексте, а не отчёт об уже выполненном вызове модели.

## 7 Контрольные точки интеграции

| Момент | Что проверяется |
| --- | --- |
| До параллельной реализации | Все используют эти ID, названия полей, схемы и одну трактовку исходного/финального результата |
| К 6-му часу | Участник 1 загружает правила и считает; участник 2 выдаёт настоящий ответ; участник 4 импортирует; карточка участника 3 принимает общий формат |
| К 12-му часу | Работает полный сценарий апелляции с сохранением после перезапуска |
| До контрольного этапа | Все 65 записей открываются, пять аудио проверены, пакетный повтор работает, выбранная модель укладывается в измеренный бюджет времени |
| После выдачи контроля | Новый group_id загружается; получены реальные оценки новых транскриптов и явно показаны ошибки |

Интервалы относительные: они отсчитываются от старта командной работы и согласуются с официальным стоп-кодом. Если времени осталось меньше, первой целью остаётся один сквозной реальный сценарий, затем расширение на весь набор.

## 8 Что уже проверено в подготовленном пакете

Действующая схема cqa-team-v1 проверяет конфигурации и публичные искусственные примеры. Доказательства ссылаются на существующие message_id в указанной группе и диалоге. Девять арифметических кейсов подключены к производственному калькулятору. Тесты импорта проверяют повтор, разделение групп и откат при изменении или исчезновении записи. Измерение точности AI в эти проверки не входит.

Реализованы модуль участника 1 и API данных ZIP в общем сервере. [Проверки интеграции](ZIP_INTEGRATION.md) и [передача участника 1](PARTICIPANT_1_HANDOFF.md) фиксируют объём. Реальная модель, UI карточки, воспроизведение и ручная синхронизация аудио, пакетная оценка и апелляции остаются задачами участников 2–4.
