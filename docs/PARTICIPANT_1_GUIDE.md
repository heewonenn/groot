## 1 Что мы должны были сделать

Ваша часть отвечает на два вопроса: **по каким правилам оценивать оператора** и **как превратить выбранные ответы в итоговый балл**.

Представьте критерий «оператор поздоровался и представился». Вы задаёте его формулировку, вес и допустимые ответы. Участник 2 подключает модель, которая читает диалог и выбирает ответ с доказательством. Ваша функция превращает этот ответ в баллы. Если проверяющий изменит ответ при апелляции, участник 3 вызовет ту же функцию.

По распределению команды мы должны были:

1. Перенести восемь критериев из PDF без изменения их исходного смысла, весов, шкал и условий N/A.
2. Сделать редактор, в котором можно создать чек-лист, добавить или заменить критерий, изменить его текст, вес, тип ответа, шкалу и объяснения ступеней.
3. Сохранять версии. Новое правило применяется в новой оценке, а прежняя оценка продолжает ссылаться на прежнее правило.
4. Предоставить участнику 2 полную конфигурацию по ID версии.
5. Написать один серверный расчёт для первоначальной оценки и пересмотра, включая N/A, отдельный флаг и округление.
6. Проверить арифметику и передать команде работающий модуль.

Версия — сохранённый снимок правил. Черновик можно менять; сохранённый снимок остаётся прежним. Например, `freedom-chat@1` и `freedom-chat@2` — две версии одного чек-листа. Это позволяет объяснить, почему один и тот же диалог получил разные оценки по разным правилам.

## 3 Какие правила нельзя потерять

В исходном чек-листе должны оставаться следующие значения. В новой пользовательской версии настройки могут отличаться — это и требуется для гибкости системы. Изменение настройки не переписывает исходную версию.

| № | Критерий | Ответ | Вес | Когда допустим N/A |
| --- | --- | --- | --- | --- |
| 01 | Установление контакта | Да / Нет | 10 | Не допускается |
| 02 | Выявление потребности | Да / Нет / N/A | 15 | Данных для ответа хватало с начала |
| 03 | Идентификация | Да / Нет / N/A | 20 | Запрос не требовал проверки личности |
| 04 | Корректная и полная консультация | 0, 5, 10, 15, 20 / N/A | 20 | Диалог закончился до формулировки запроса клиентом |
| 05 | Эмпатия и клиентоориентированность | Да / Нет | 15 | Не допускается |
| 06 | Управление диалогом, скорость и грамотность | 0, 4, 7, 10 | 15 | Не допускается |
| 07 | Завершение | Да / Нет / N/A | 5 | Диалог оборвался до возможности завершения |
| 08 | Грубые ошибки | Да / Нет | 0, отдельный флаг | Не допускается |

«Нет» означает, что действие требовалось, но выполнено неверно или пропущено. Его вес остаётся в расчёте. N/A означает неприменимость по разрешённому условию: такой вес исключается, а остальные пропорционально нормируются на 100. Отсутствие информации или сбой модели нельзя автоматически превращать в N/A.

Три разных числа: модель выбрала ступень **7**, вес критерия — **15**, начислено до перераспределения **10,5**. Формула: `7 / 10 × 15`. После исключения N/A вклад в общий итог может отличаться от 10,5.

Общий итог: `100 × сумма начисленных баллов / сумма применимых весов`. Если применимых весов нет, результат — `null` с объяснением, а не 0 или 100. Итог округляется до двух знаков. `ROUND_HALF_UP` — выбранное командой явное правило округления; сам PDF не уточняет обработку половинного значения. В согласованном примере 88,125 превращается в 88,13.

Флаг 08 отмечает грубое нарушение отдельно и не обнуляет итог. Порог первой реакции в три минуты, теги и вложения в данную оценку не входят. Бот и системные события могут быть контекстом или доказательством события, но приветствие бота нельзя засчитать оператору.

Для звонков критерий 04 оценивает корректность и полноту консультации. Критерий 06 относится к понятности устной речи, логике разговора, уместности формулировок и управлению паузами. Темп, дикцию и произношение можно оценивать при фактическом анализе аудио. Само наличие ссылки на запись не означает, что модель её слушала. Распознавание речи с нуля не обязательно: транскрипты выданы организаторами.

Калькулятор проверяет допустимость ответа и арифметику. Смысл ответа, истинность N/A и доказательства проверяет модуль оценки. Если модель правильно оформила ошибочное суждение, одной математической проверки недостаточно.

## 4 Как запустить вашу часть

Рабочая папка: `C:\Users\1\Documents\ChatGPT\GROOOOOT`. Вчера установленные зависимости уже находятся здесь; перед обычным запуском переустанавливать их не нужно.

Первый терминал PowerShell — сервер:

```powershell
Set-Location -LiteralPath 'C:\Users\1\Documents\ChatGPT\GROOOOOT'
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --reload --host 127.0.0.1 --port 8765
```

Второй терминал PowerShell — интерфейс:

```powershell
Set-Location -LiteralPath 'C:\Users\1\Documents\ChatGPT\GROOOOOT\frontend'
npm run dev
```

Откройте [редактор чек-листов](http://127.0.0.1:5173/checklists). Оба терминала должны продолжать работать. Сервер предоставляет данные и считает; интерфейс показывает страницу. Остановка — `Ctrl+C` в соответствующем терминале.

В VS Code уже настроены задачи: через `Terminal → Run Task` можно выбрать `Backend: dev`, `Frontend: dev` и `Verify workspace`. Для Python выбранным интерпретатором должен быть `.venv\Scripts\python.exe` из этого проекта.

Чек-листы сохраняются в `data/cqa.sqlite3`. Этот файл создаётся автоматически и исключён из Git. Не удаляйте его для обычного перезапуска: там пользовательские версии. Для новой копии проекта предусмотрен `scripts/setup.ps1`; установка и проверка на втором компьютере ещё должны быть выполнены командой.

Дополнительно через `$hackathon-qa` проверить: пустой публикуемый чек-лист; дубли ступеней; неверный вес; старую редакцию из второй вкладки; отсутствующий ответ; запрещённый N/A; отсутствие применимого веса. Полная автоматическая проверка из корня проекта:

```powershell

```

Сначала остановите запущенные вами dev-серверы на портах 8765 и 5173: проверка поднимает свои серверы. Тесты используют временную базу с искусственными данными. Успех — завершение команды без ошибки и строки о прошедших тестах. Если процесс завис, это не считается успешным тестом. В среде Codex уже встречалось ограничение loopback-сокетов песочницы; оно решалось разрешённым запуском локальных проверок вне неё, без отключения защиты Windows.

## 6 Что осталось до готового MVP

### Приоритет 1 — связать вашу часть с настоящей оценкой

Совместно с участником 2 пройти сценарий на подготовленном `p1-ru-014`, где оператор здоровается, но не представляется:

1. Получить настоящий модельный ответ по `freedom-chat@1`. По критерию 01 ожидается «Нет» с конкретной репликой.
2. В редакторе убрать только требование представиться и сохранить новую версию.
3. Повторно запустить оценку того же транскрипта по новой версии. Ожидается «Да» со ссылкой на ту же реплику.
4. Открыть обе оценки: их версии и ответы отличаются; прежний результат сохранён.
5. Проверить, что новый запуск действительно использовал новое правило, а не старый кеш или заранее написанный ответ.

Ваша сторона этого сценария — создание и выдача версии — работает. Сам реальный вывод модели ещё не проверен. Отдельно нужен тест добавления совершенно нового критерия: это подтверждает, что оценщик не привязан к восьми жёстко заданным полям.

### Приоритет 2 — подключить настоящий пересмотр

Вместе с участником 3 пройти апелляцию: комментарий → решение с причиной → вызов общего расчёта → сохранение оригинала и финального результата → обновление страницы. Затем повторить пересмотр старой оценки после создания новой версии чек-листа: она должна пересчитываться по исходной версии.

Для удобной проверки арифметики используются 85,38 и 93,08. Реальная модель не обязана выдать эти числа на выбранном DEV-чате: они не являются эталонными оценками этого диалога.

### Приоритет 4 — подтвердить качество оценки

Главный ориентир отбора — точность относительно Ground Truth на десяти неизвестных транскриптах. Красивый редактор и проходящие тесты калькулятора сами по себе это не подтверждают.

Участнику 2 нужна независимая ручная проверка ответов, причин N/A и доказательств на RU, KZ и EN. Команде нужно записывать ошибки и реальные измерения. Внутренние показатели можно использовать для сравнения вариантов, но точная официальная формула сравнения и проходной порог пока не объявлены. Контрольные ответы нельзя подменять фикстурами или заранее подготовленными результатами.

Для критерия 04 необходимы актуальные продуктовые материалы, если вывод касается фактической корректности тарифа или услуги. Присланный `Data 2 (1) 1.pdf` — общая презентация компании и экосистемы; он не содержит полного справочника ответов по консультациям. Отдельные эталонные ответы контрольных диалогов организаторы не предоставили.

Дополнительные факторы отбора — полезные функции, удобство, корректность процесса и представительство разных архитектур. Это не требование запускать одновременно несколько моделей или обязательно обучать свою. Не следует тратить время на дополнительные графики, собственное распознавание речи или новые интеграции, пока основной сценарий и качество оценки не проверены.

Регистрация и вход для демонстрации не требуются. Интерфейс должен оставаться веб-интерфейсом, пригодным для будущей адаптации под HTML-компонент Dynamics 365; готовая интеграция с Dynamics сейчас не заявлена выполненной. Публичная сдача, срок стоп-кода и пятиминутная защита — общие требования, которыми занимается команда с участником 4.

Локальные навыки проекта уже доступны из `.agents/skills`. Их можно явно назвать в запросе; в Codex CLI и IDE есть выбор через `$` и `/skills`. [Официальная документация навыков](https://learn.chatgpt.com/docs/build-skills).

В этом этапе использованы проверка по `hackathon-qa`, официальные OpenAI Docs и чтение исходных PDF. Ранее реализация модуля выполнялась с инструкциями `backend-engineer` и `frontend-design`. Для вашей роли не требуется устанавливать ещё один набор библиотек только ради количества инструментов.

## 8 Какие возможности Codex полезны здесь

| Возможность | Практическая польза | Состояние и применение |
| --- | --- | --- |
| Контекст проекта и `AGENTS.md` | Сохраняет правила командной работы, стек и команды проверки | Уже используются в этом проекте |
| Чтение файлов, выполнение команд и правка кода | Можно попросить не только объяснить, но и реализовать, запустить и проверить изменение | Уже применялось при создании модуля |
| Playwright | Открывает приложение и проверяет настоящие клики, формы и связь с API | Установлен; 6 браузерных сценариев входят в проверку |
| OpenAI Docs | Позволяет проверять актуальные возможности Codex по официальным источникам | Доступен и использован при подготовке инструкции |
| Просмотр изменений и `/review` | Помогает увидеть, какие файлы менялись, и найти ошибки перед объединением | Использовать с указанием файлов участника 1; обзор не заменяет тесты |
| Отдельные ветки и worktrees | Позволяют вести независимые изменения в разных копиях проекта | Нужна общая исходная версия в Git и настройка зависимостей каждой рабочей копии |
| Специализированные агенты | Можно явно поручить одному backend, другому интерфейс, третьему проверку | Роли уже настроены; разные агенты не должны одновременно править один файл |
| Figma | Полезна для реализации конкретного согласованного дизайна | Инструмент доступен; для этой работы отдельный макет не задан |
| GitHub | Помогает работать с репозиторием и ревью команды | `origin` настроен; доступ к конкретному репозиторию и синхронизация этой работы ещё не подтверждены |

Для просмотра изменений в приложении доступна панель review, а `/review` позволяет запросить проверку локальных изменений. Проверяйте замечания по реальным строкам кода и сценариям. [Официальная документация code review](https://learn.chatgpt.com/docs/code-review?surface=app).

Worktree — отдельная рабочая копия того же Git-проекта. Она помогает изолировать параллельные изменения, но не передаёт автоматически базу, секреты и установленные зависимости. Новый чат в той же обычной папке сам по себе изоляции файлов не создаёт. [Официальная документация worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees).

В проекте есть пять конфигураций ролей: `backend_engineer`, `frontend_engineer`, `qa_engineer`, `ml_engineer`, `architecture_reviewer`. Наличие конфигурации не означает, что все агенты постоянно работают. Для большой независимой задачи можно прямо написать: «Поручи backend и frontend разным агентам, закрепи за ними разные файлы, затем проверь объединённый результат». Для небольшой правки достаточно одного агента.

Проверены локальные CLI-профили: `hackathon-quality` настроен на `gpt-6-astra / ultra`, `hackathon-routine` — на `gpt-6.1-sol / low`. Первый предусмотрен рабочими правилами для сложных решений и проверок, второй — для небольших правок. Это существующие настройки данного компьютера; выбор в уже открытом чате проверяется отдельно. Профили не выбирают модель-оценщик CQA и не означают подключение платного API к продукту.

Установленные React, TypeScript, FastAPI, Pydantic, Axios, Lucide, Ruff, ESLint и Playwright уже используются по назначению. Pandas, Jupyter и scikit-learn пригодятся для данных и экспериментов, если их потребует участник 2; Recharts нужен при наличии настоящих данных для графиков. Дополнительная установка всех доступных плагинов не является этапом готовности MVP.

## 9 Как работать вчетвером

Ждать окончания чужой роли не нужно. Согласуйте общий формат, получите одну исходную версию проекта и работайте в отдельных ветках. Для вас — ветка вида `codex/checklists`; для остальных — их ветки и закреплённые модули. `main.py` и `App.tsx` объединяет участник 4, поскольку это общие точки подключения.

Участник 2 уже может получать конкретную версию правил и transcript из общего API. Участник 3 может строить карточку на согласованном демонстрационном ответе с явной отметкой demo. Участник 4 продолжает аудио и выпуск на основе подключённого импорта ZIP. После небольших готовых изменений нужно соединять части и проверять общий сценарий, не откладывая первое объединение до финала.

На момент проверки в локальном Git ещё нет коммитов; адрес `origin` уже задан. Это не подтверждает, что нынешний код есть у остальных. Перед началом совместной интеграции нужно согласовать исходный коммит и передачу кода. Секреты, подписанная ссылка организаторов, локальная база и приватные записи не должны попадать в общий публичный репозиторий. Отправка кода и публикация в рамках подготовки этой инструкции не выполнялись.

Ваша часть считается принятой командой, когда её можно запустить по инструкции, получить версию правил, посчитать принятые ответы, применить новый критерий с настоящей моделью и пересчитать старую оценку после апелляции. Первые три пункта подтверждены локально; последние два требуют совместной интеграции.
